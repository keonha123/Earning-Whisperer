# 인접 어닝콜의 시작시각 자동 수집과 DB 통합

2026-09-23. 대상은 과거 버전 data_pipeline이며 캡처 동시성은 변경하지 않는다.

## 정상 흐름

1. 전 종목의 넓은 일정은 기존 날짜 수집·교차 확인으로 유지한다.
2. 기존 10분 주기 `ScheduleService.enrich_schedule_times`가 미확인 또는 재확인 시점에 도달한 일정을 고른다. 기본 조회 범위는 14일, 한 번에 최대 20개다. 가까운 일정부터 처리하며 확인한 시각도 재확인한다.
3. 공식 IR·행사 상세 페이지를 HTTP로 먼저 읽는다. 정확한 시각이 없을 때 행사 현지 날짜 기준 기본 −2~+2일의 일정에 한해 Chromium으로 렌더링한다. 공식 행사 카드가 연결한 제공사 페이지도 한 곳까지 읽을 수 있다. 로그인·재생 없이 회사·행사·일자·시간대를 확인한다.
4. UTC 시작시각을 `calls.scheduled_at_utc`에 저장한다. `webcast_date`, `source_timezone`, `schedule_source`, `schedule_evidence`, `time_verified_at`도 함께 저장한다. 실적 보도자료 공개시각, 사전 녹음 공개시각, 재생 가능 종료일을 실제 콜 시작시각으로 쓰지 않는다.
5. 실제 감시 브라우저가 먼저 정확한 시각을 찾은 경우에도 같은 저장 로직을 재사용한다. 브라우저 관측은 정규화한 오류 문자열이 아니라 날짜·시각·시간대·행사 경로 증거를 가진 구조화된 값이다. 부모 프로세스에서 회사·날짜·공식 출발 경로·제공사 행사 ID·관측 신선도를 다시 검증한다.
6. 탐색 소유권 해제와 시각 저장을 하나의 DB 트랜잭션으로 처리한다. 대기 시각은 DB 시작시각에서 기본 5분을 뺀 값이다. 과거 오류 메시지에 남은 시각이 DB 시각을 덮어쓰지 못한다.

## 변경·불확실성 처리

- 시각이 앞당겨지거나 연기되면 `schedule_revision`과 변경 이력을 갱신하고 이전 대기·탐색 캐시를 무효화한다. 다음 일반 감시 주기가 새 DB 시각으로 재탐색한다.
- 새 시각이 다른 일정 버전을 만들었다면 이전 버전으로 연 브라우저를 그대로 캡처로 승격하지 않는다. lightweight 탐색에서 시각을 얻으면 등록·오디오 단계 전에 먼저 저장한다.
- 오래된 관측, 다른 worker 소유의 탐색, 만료된 lease, 이미 바뀐 revision은 거부한다. running/completed 수집은 정규 시간 갱신으로 덮어쓰지 않는다.
- 날짜 자체의 이동은 기존 공식 행사 동일성 검증·일정 재조정 경로가 담당한다. 브라우저의 다른 행사 날짜 하나만으로 현재 콜 일자를 바꾸지 않는다.
- 시간대가 없거나 시각이 충돌하면 정확한 시각을 추측해서 저장하지 않는다. 기존 일자 기반 감시와 재확인 경로를 유지한다. 제공사에서 확인한 시각을 상위 IR 카드에 시각이 없다는 이유만으로 지우지 않는다.
- 같은 날짜의 다른 후보로 이동하거나 명시적 시각 충돌이 발견되면 앞서 읽은 브라우저 관측을 재사용하지 않는다.

## 비용·시간 제한

| 환경변수 | 기본값 | 의미 |
|---|---:|---|
| SCHEDULE_TIME_BROWSER_DAYS_AHEAD | 2 | 상세 브라우저 확인을 허용할 향후 날짜 범위 |
| SCHEDULE_TIME_BROWSER_PAGES_PER_CALL | 2 | 일정 한 건의 브라우저 페이지 수 |
| SCHEDULE_TIME_BROWSER_SECONDS_PER_CALL | 60 | 일정 한 건의 브라우저 처리 예산(초) |
| SCHEDULE_TIME_BROWSER_PAGES_PER_REFRESH | 6 | 갱신 배치 전체의 브라우저 페이지 수 |
| SCHEDULE_TIME_BROWSER_SECONDS_PER_REFRESH | 120 | 갱신 배치 전체의 브라우저 예산(초) |
| SCHEDULE_TIME_BROWSER_PAGE_TIMEOUT_SECONDS | 35 | 한 브라우저 페이지 처리 상한(초) |

한 번의 갱신 안에서 같은 HTTP/브라우저 페이지를 재요청하지 않는다. 브라우저는 미디어·이미지·폰트 요청을 차단한다. 시간 갱신 자체는 검색 API 키가 없어도 알려진 공식 경로에서 동작한다. 공식 경로를 모르는 경우나 접근 장벽은 여전히 미확인으로 남을 수 있다.

## 확인 방법

`calls`에서 UTC 시각·시간대·출처·확인시각·revision을 함께 본다. 시각만 SQL로 수동 입력하지 않는다.

운영 로그 `schedule_enrichment`는 조회 페이지 수, 브라우저 사용 시간, 예산 제한, 충돌을 기록한다. `browser_schedule_time`는 브라우저가 얻은 시각의 저장/거부 결과를 기록한다. 해당 탐색의 `live-runs/<call_id>/<attempt_id>/schedule.json`에는 `browser_start_observed`, `browser_start_committed`, 거부 또는 초기화 사건이 남는다. completed 콜의 과거 시각을 이번 배포에서 수동 보정하지 않는다.

검증은 공통 시간 파서, 실제 SQL 트랜잭션, stale 관측 거부, 시각 앞당김·연기와 대기 재계산, 브라우저→DB 전달, JavaScript 지연 렌더링, 사전 발표와 실제 Q&A 분리를 포함한다. 실제 외부 사이트마다 시작시각을 반드시 얻는다는 보장은 아니다.
