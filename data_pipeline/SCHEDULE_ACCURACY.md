# 일정 후보 정확도 개선 (2026-09-18)

이 문서는 과거 버전 data_pipeline의 일정 → 공식 행사 확인 → 브라우저 감시 연결을 설명한다.
실제 콜의 전체 재생·수집 성공률을 의미하지 않는다.

## 공식 행사와 경로 선택

- 저장된 상세 페이지와 현재 공식 IR 페이지를 함께 확인한다. 날짜만 발견했다고 조기 종료하지 않는다.
- 제목·날짜·회계기간·웹케스트 버튼이 같은 행사 영역에 있는지 확인한다. 다른 카드나 과거 발표자료의 날짜/분기를 빌리지 않는다.
- 광고·추적 URL, PDF·이미지·캘린더 파일은 재생 후보에서 제외한다. URL이나 쿼리에 earnings/webcast라는 단어가 있는 것만으로는 증거가 되지 않는다.
- 회사 페이지가 직접 연결한 새 공급자도 허용한다. 공급자 도메인 목록에 없다는 이유만으로 제외하지 않는다.
- 공식 경로 증거 `issuer-route-v2`에는 회사, 행사 날짜, 회계기간, 행사 종류, 출처와 정확한 목적지 URL을 저장한다. 기존 `target-linked` 문자열만 있는 기록은 브라우저 재탐색을 거친다.
- DB의 기존 `call_year/quarter`는 달력 분류이므로 실제 콜의 회계분기를 강제하지 않는다. 회사가 명시한 값은 `verified_fiscal_year/quarter`에 별도로 저장한다.

## 시각과 변경 처리

- `8 a.m.`, 여러 줄에 나뉜 제목/시각, `Sep. 23`, `01 October, 2026`, HTML time 및 JSON-LD를 처리한다.
- 실적 자료 공개 시각, 사전 녹음, 재방송을 실제 콜 시작과 구분한다. 근거가 충돌하거나 DST 때문에 모호하면 확정하지 않는다.
- ICS 파싱은 지원하지만 캘린더 링크 자동 수집까지 구현된 것은 아니다.
- 갱신 작업 기본 주기 10분, 오늘/내일 행사의 재확인 자격 10분이다. 한 번에 20개라는 처리 한도와 사이트별 오류 대기 때문에 모든 행사가 정확히 10분마다 조회된다는 보장은 없다.
- 공식 페이지를 성공적으로 읽었는데 시간이 철회·미정·연기로 바뀌면 이전 시각을 확정값으로 쓰지 않는다. 취소된 행사는 감시에서 제외한다. 단순 네트워크 오류는 기존 관측값을 지우지 않는다.
- 120분 이상 재확인하지 못한 시각은 좁은 시간 창만으로 감시를 막지 않고 날짜 기반 감시로 돌아간다. 이전 관측값은 진단용으로 보존한다.
- 2일을 넘는 날짜 이동은 같은 행사라는 공식 근거가 있을 때만 수용한다. 회계분기가 명시된 유일한 인접 공식 행사 등 강한 근거로 후보를 다시 식별한다.

## 저장·실행 일관성

- `schedule_revision`과 관측 시각으로 오래된 응답의 덮어쓰기를 막는다. probe 실행권을 얻을 때도 조회 당시 revision을 비교한다.
- 날짜·시각·경로가 달라지면 이전 탐색 결과와 재시도 대기를 무효화한다.
- 변경 전후는 `schedule_change_history`에 저장한다. 단순 재확인만으로 이력을 계속 늘리지 않는다.
- 같은 공식 행사로 확인된 미수집 중복은 대표 행을 가리키게 하고 중복 실행을 막는다. 기존 호출 ID는 유지한다.
- 탐색/수집 중인 행, 완료된 행, 수집·텍스트 이력이 있는 행은 자동 병합으로 지우지 않는다.

## 진단과 검증

읽기 전용 진단:

```sh
python -m data_pipeline.collectors.schedules.enricher --dry-run --call-json /path/to/calls.json --workers 2
```

입력은 ticker, ir_url, earning_at 또는 webcast_date, 선택적 event_url 및 검증된 회계기간을 포함한 배열이다.
`--call-json`과 `--dry-run` 조합은 운영 DB를 읽거나 쓰지 않고, 외부 검색 API를 호출하지 않는다.
결과에는 확인한 페이지, 시각, 후보, 충돌 여부, 사이트 접근 실패가 나온다.

검증 범위:

- 로컬 회귀: 행사 영역 혼합, 광고/PDF 오인, 날짜/시각 형식, 시각 철회, 오래된 시각, 경로 증거 전달.
- 격리 MySQL: 기존 스키마 반복 업그레이드, 기록 보존, 일정 변경과 중복, 동시 갱신, 실제 후보 SQL와 probe revision 비교.
- 실제 공개 페이지: Cintas, Paychex, Accenture의 DOM으로 행사·시각·경로를 대조했다.
- 일부 공식 사이트는 현재 실행 환경에서 HTTP 403 또는 응답 시간초과가 발생한다. 이런 사이트까지 해결되거나 500개 기업 모두의 시간이 확보된 상태는 아니다.
- 다음 실제 생방송에서 변경 감지부터 재생·텍스트 저장까지 별도 확인이 필요하다.

실행 로그와 반영 결과는 `.runtime/schedule-accuracy-20260918/`에 보존한다.
