## 로그와 현장 확인

기존 `.runtime/live-runs/<call_id>/<attempt_id>/`에서 단계별 증거를 확인한다.

- `registration_validation`: 실제 필드 오류 수와 `unresolved_choice_count`를 분리한다. 정상 텍스트 입력을 선택 실패로 오인했는지 구별할 수 있다.
- `schedule`의 `browser_clock_retained` / `browser_clock_conflict`: 후속 탐색 실패에서 시각이 보존됐는지, 실제 상충으로 재확인이 필요한지 확인한다.
- `discovery`의 `official_route_reused`: IR 차단 대기 중에도 검증된 직접 주소를 재사용한 근거를 남긴다.
- `browser`의 `barrier_evaluated`: main/frame, 가시성, 흐름 관련성, 관측 가능 여부와 차단 규칙을 기록한다. 폼 값이나 CAPTCHA 본문은 기록하지 않는다.
- 새 `capture_source.json`과 `events.jsonl`: 현재 행사에서 관측한 HLS 갱신, 재생목록 길이·종료 태그, 활성 플레이어 수를 기록한다. 미디어 URL/토큰은 저장하지 않는다.

상태 확인 예시:

```sh
docker exec ew-pipeline-scheduler python -B -m data_pipeline.tools.debug.live_control status --call-id 120
```

출력의 `live_verification`은 DB의 `completed`나 전사 행 수만으로 생방송 성공을 선언하지 않는다. 같은 call/ticker/session/revision에 속하는 최근 120초 관측만 현재 상태로 사용하고, 오래된 관측은 시각과 함께 과거 근거로 표시한다.

`source_phase` 의미:

- `identity_unverified`: 현재 페이지의 행사 식별 근거가 유효하지 않음.
- `waiting_for_start`: 기존 감시 로직이 방송 전 대기로 판단함.
- `live_transport_observed`: 같은 행사 페이지의 HLS가 실제로 증가/전진함. 발화 내용이나 플레이어와 해당 요청의 일대일 연결을 확정한 것은 아님.
- `replay_candidate`: 긴 종료된 재생목록과 긴 유한 플레이어가 관측됨. 검토가 필요한 다시보기 후보이며 이것만으로 캡처를 끊지 않음.
- `unconfirmed`: 근거가 부족함. 단일 HLS 요청, 지원하지 않는 전달 형식, 오래된 관측을 생방송으로 추정하지 않음.

이 관측기는 브라우저가 이미 받은 크기가 명시된 비압축 HLS 응답만 읽으며 외부 요청을 추가하지 않는다. 압축/길이 미상/과대 응답과 다른 행사 프레임은 제외한다. ENDLIST만으로 종료를 선언하지 않아 대기음악·광고 때문에 방송을 놓치지 않는다. 최근 transport 시각과 플레이어 끝 위치도 서로 다른 미디어일 수 있어 별도 관측값으로만 남긴다.

## 검증과 적용

최종 검증 대상은 관련 33개 모듈의 463개 테스트이며 미해결 실패/생략은 없다. 전체 실행에서 462개가 통과했고, 실제 3브라우저 오디오 검사는 테스트 마운트가 읽기 전용이라 준비 신호 파일을 쓰지 못했다. 소스를 바꾸지 않고 컨테이너 전용 writable tmpfs 런타임을 제공해 이 1개를 재실행하여 통과했다(전체 174.028초, 오디오 재검사 57.706초). 원 실행 로그와 환경 실패 및 재실행 결과를 함께 보존한다.

실제 Chromium으로 폼·iframe·수동 인증 장벽·동적 시작시각 수집을 검증했다. 오디오 검사는 3개 브라우저에서 440/660/880Hz를 별도 PulseAudio로 재생하여 혼선 기준을 만족하고, 하나를 종료해도 나머지 두 개가 유지되는 것을 확인했다. 외부 서비스와 STT 모델은 이 오디오 검사에 사용하지 않았다.

추가 검사에서 새 URL 검증이 정상 비표준 HTTP(S) 포트도 거절하던 호환성 문제를 발견해 배포 전에 수정했다. 정상 포트는 허용하고 0·음수·문자열·범위 초과 포트와 잘못된 주소는 계속 거절한다. 기존 행사·날짜·issuer·인증 검증은 유지한다.

개별 검증: 입력폼 94개, 인증장벽 171개, 시각·주소 복구 197개 통과. 이 수치는 통합 검사와 중복되므로 합산하지 않는다. 실제 COST의 당시 schedule.json을 고정된 당시 시각으로 재현하여 UTC 21:00 보존, URL 문자열 타입 유지, 다음 감시의 verified provider 재시도, 불필요한 IR subprocess 0회를 확인했다.

원본 SHA256을 검증하고 변경 파일만 백업한 후, 실행 중인 캡처/탐색이 없는 상태에서 적용한다. 배포 시각·전후 상태·파일 해시·테스트 로그는 `.runtime/failure-fixes-20260927/`에 기록한다. DB 스키마와 과거 결과의 수동 변경은 없다.

## 해석상의 한계와 후속 확인

COST의 과거 미수집분이나 GIS의 놓친 전반부를 이 수정이 되살리지는 않는다. CTAS의 같은 날 다시보기와 PAYX의 원 생방송 이후 재수집도 과거 이력 그대로 남는다.

이번 검증은 실제 Chromium을 사용하는 로컬 폼/iframe 테스트, 당시 저장된 COST 증거의 재현, 감시·저장·종료·동시성 회귀다. 각 업체의 다음 실제 생방송에서 최소조건(올바른 생방송에 접근해 실제 발화를 한 건 이상 저장)을 확인해야 한다. 새로운 source 진단은 오디오와 텍스트의 정답 검증이나 음악 환각 판별기를 대신하지 않는다.

추가 잠재 위험: `_page_http_status`는 현재 agent의 마지막 탐색 응답값이다. 다른 탭/팝업에 과거 403 상태가 전파될 가능성은 별도로 남아 있으며, 이번 과거 실패의 직접 원인으로 확정되지는 않았다. 탭/응답 소유권을 함께 기록해 재현하는 후속 검토가 필요하다.
