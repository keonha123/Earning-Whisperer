# 과거 어닝콜 접근 실패의 원인 분석 — 2026-09-27

대상: 과거 프로젝트 `/home/dheorb/workspace/projects/school/Earning-Whisperer`. 이번 작업은 원인 규명이며 운영 코드·DB·프로세스를 변경하지 않았다. 과거 로그·DB 이력·실패 화면·당시 수정본/백업·현재 코드를 대조했고, 새 결함은 외부 네트워크가 차단된 별도 Chromium 또는 DB를 쓰지 않는 함수 재현으로 확인했다.

## 판단 기준

네 건을 모두 후보 탐색 실패로 묶으면 서로 다른 결함에 같은 수정을 적용하게 된다. 이 네 건을 전체 종목의 성공률 표본으로 쓰지는 않는다.

## 1. COST: 찾은 정보가 있었지만 다음 단계에서 잃었다

올바른 당일 Q4 행사 `events.q4inc.com/attendee/186598450`까지 여러 번 도착했다. 9/23~24 실제 시도 네 번에 제공사 화면의9/24 21:00UTC(9/25 06:00KST)가 browser_start_observed/verified로 기록됐다. 정확한 시간 파싱은 성공했다.

### 정상 입력을 잘못 차단한 폼 판정

최초 시도는 제출 로그 이후 등록 단계30초 시간초과였으며 실제 서버 응답은 증거가 부족하다. 이후 세 번의 registration 진단은 native invalid_field_count=0, visible_error_count=0, 회사명 선택 selected_matches=true, company_role 입력 성공이었다. 그런데 이후 company_role을 선택형으로 다시 검사해 choice_menu_not_found를 추가하고, 이를 필수입력1개 누락처럼 합산하여 제출 전 차단했다.

현재 `registration.py`의 choose_option_field label fallback은 native select가 아니면 일반 input인지 확인하지 않고 structured choice로 넘길 수 있다. 실제 Chromium fixture에서 required Company Role input에 값이 채워져 있고 native validation 오류가 없는데도 원본 전체 등록 함수가 동일한 오류로 제출0회를 반환했다. 사이트가 입력을 거절하기 전에 우리 코드가 멈춘 것이다.

### 정확히 읽은 시간의 전달 소실

`manager.py:565` 부근에서 각 경로 탐색 뒤 `_browser_schedule_observation`을 지우고 현재 경로의 신원 확인이 성공할 때만 다시 넣는다. 첫 Q4 경로에서 읽은 정확한 시간이 두 번째 IR 실패에서 삭제되고, 전체 경로가 끝난 뒤 저장 호출에는 전달되지 않았다. 실제 당시 observation은 파일에 남아 있고 검증 함수도 통과한다. 원본 경로 순회 함수를 이용한 재현에서도 Q4 뒤 true→IR 실패 뒤 false→최종 false를 확인했다.

따라서 DB 시각 NULL은 외부 페이지에 시간이 없었다는 증거가 아니다. 이 사례에서는 **수집한 근거의 전달 손실**이다.

### 인증 판정과 재시도 경로의 결합

IR/event 경로는 captcha로 분류되어12시간 보호 대기에 들어갔다. 마지막 구간은9/25 01:05~13:05KST로 실제 콜06:00이 포함됐다. 다만 당시 화면에는 정상 행사와 웹캐스트 링크가 보였다. 현재 차단 판정은 iframe 가시성을 검사하지 않고 본문에 captcha가 있으면 반환한다. 정상 페이지+숨은 인증 iframe만으로도 CAPTCHA가 재현된다. 당시 DOM의 iframe 가시성은 보존되지 않았으므로 실제 challenge 여부를 단정하지 않는다.

상위 discovery가 IR에서 행사 동일성을 다시 확인하지 못하면 직접 Q4 경로에 재진입하지 않는다. 따라서 직접 웹캐스트에12시간 보호 대기가 없는데도 공식 IR의 대기가 직접 폼 복구까지 막았다. 보존된 공식 근거 우회는 오래된9/14 확인시각과 구조화 증거 부재 때문에 통과하지 못했다. 반복1,433건은 실제 접속1,433회가 아니라 상당수가 접속 전에 반환된 검사다.

이전 보고의 '필수값을 입력하지 못했다', '실제 CAPTCHA에 막혔다', '시간을 확보하지 못했다'는 설명은 각각 위와 같이 더 정확히 정정한다.

## 2. CTAS: 틀린 후보를 골랐던 것이 아니라 맞는 후보를 거절했다

전날부터9/23 14:00UTC(23:00KST) 시작 시각이 저장돼 있었다. 첫 시도13:40UTC에 당일 Q1 FY2027 등록 화면에 도착했고 공식 링크 근거도 있었다.

저장 주소는 `/mmc/p/6agfne3p`, 표시 주소는 `/mmc/p/6agfne3p/`였다. History API 정규화는 HTTP redirect로 잡히지 않았고 당시 provider ID 지원도 없어, 신원 검증이 같은 행사라는 사실을 유지하지 못했다. 13:40~15:25UTC47회 반복해서 폼 제출 전에 실패했다. 재시도 루프가 멈춘 사례가 아니다.

해당 제공사의 동일 행사 ID에서 끝 슬래시 차이를 허용한 뒤 등록·재생·STT는 통과했다. 하지만 수정 후15:27UTC부터 나온 개회는 ENDLIST가 있는64분39.888초 녹음이었다. 같은 당일 행사의 재방송216구간이며 최소 생방송 성공으로 세지 않는다. 이 주소 비교 결함은 이미 수정된 범위다.

## 3. GIS: 맞는 후보에 도달했지만 시간·폼 때문에 늦었다

21:56KST Q4에서 정확한22:00 시작 시각을 확보했다. 회사명 입력의 검색 문자열을 실제 선택 완료로 잘못 처리해 폼이 남았고, 대체 IR 카드의08:00CST가 제공사13:00GMT를 덮어 한 시간 늦게 기다리는 상태로 바뀌었다.

22:10 시각 복구 뒤에도 폼 밖에 열린 회사명 메뉴를 찾지 못해 실패가 이어졌다. 폼 내부 옵션0개·문서 전체 옵션9개가 실제로 기록됐다. 메뉴 소유권을 확인해 정확한 회사를 선택하도록 수정한 후22:32 등록·재생·저장이 성공했고22:39 종료 발언까지26구간을 얻었다. 최소 조건은 충족했지만 앞부분을 놓쳤고 실행 중 복구 개입이 있었다.

### 이번에 새로 확인한 URL 저장 결함

`browser_observation.py:116`의 target은 웹캐스트 주소인데142~145줄이 이를 기존 시작 시각으로 덮고156줄에서 webcast_url로 반환한다. 시각 변수와 URL 변수를 재사용한 버그다.

당시 시각 복구에서22:10:20 DB에 `webcast_url='2026-09-23 14:00:00+00:00'`가 실제 저장됐고22:14:15 정상 링크로 복원됐다. 최초 GIS 실패와 별개로 복구 과정에서 생긴 추가 결함이며 **현재 코드에도 남아 있다**. 현행 함수에 실제 관측을 넣었을 때 기존 시각None이면 URL, 기존 시각13/14UTC가 있으면 datetime을 반환한다.

현재 DB에서 이 형태의 잘못된 주소는0개이며, 조사한 변경 이력에서 실제 사례는GIS1건이다. 영향은 유효한 브라우저 관측·기존 시각·저장 소유권 조건을 충족한 경로다. 동일 시각을 재확인할 때도 발생할 수 있다. 저장 경계가 URL 형식을 검증하지 않아 문자열로 수용한다는 이차 결함도 있다.

## 4. PAYX: 초기 실패, 첫 생방송, 재생본을 따로 보아야 한다

9/18 이전에는 과거 Q4 자료와 다음 Q1 행사 영역이 섞인 문제가 있었다. 9/20~22 후보 확인 실패37건도 확인되지만 개별 DOM 목록이 없으므로 모두 같은 과거 자료 오선택이라고 단정하지 않는다. 별도로 오디오 준비까지 된8회는 mark_call_running 함수 인자 불일치로 캡처 승격이 실패했다. 이것도 사이트 탐색 실패와는 다르다.

9/23에는21:54등록 통과,21:55캡처 시작,22:30~31대기 안내,22:33개회,23:51폐회까지 첫 세션에 저장됐다. 당시 시각이 박힌 연속 미디어 구간과 사전 대기→개회 흐름, 이후 재생본의 다른 미디어 경로를 함께 대조했으므로 실제 생방송이라는 근거가 강하다. 첫 세션은 최소 조건을 충족한다.

문제는 이후다. 종료 안내를 이미 저장했지만600초 무발화 제한으로 실패 처리·재시도했다. 다음 접속은 같은 콜 녹음을 처음부터 재생했고71구간이 추가됐다. 이 세션을 첫 생방송304구간과 섞으면 생방송 성공 여부를 잘못 판단한다. 종료 처리와 재수집 방지는 이후 개선됐지만, 동일 행사와 실제 생방송의 구분은 여전히 결과 데이터에 명확히 남길 필요가 있다.

원음은245MB PCM으로 보존돼 있다. 이번에는 청취·정답 전문 대조를 하지 않았으므로 전사 정확도와 완전한 무손실까지 주장하지 않는다.

## 공통 결함과 수정 순서

핵심은 모든 사이트를 더 오래 검색하는 것만으로 해결되지 않는다는 점이다. 맞는 후보, 올바른 시각, 채워진 입력값을 얻은 뒤에도 단계 사이에서 잘못 거절하거나 삭제하는 결함이 있다.

| 우선 | 수정 대상 | 반드시 재현·검증할 조건 |
|---|---|---|
| 1 | URL와 시각 변수 분리, DB쓰기 전 URL타입·형식 검증 | 기존 시각이 없을 때/같을 때/변경될 때 모두 원래 검증된 주소 유지. datetime 주소 저장 거절 |
| 2 | 일반 input/native select/custom combobox를 실제 제어 형태로 구분 | COST 일반 Company Role 입력은 메뉴 없이 통과. GIS 검색형 회사명은 선택 확정 전에는 통과하지 않음 |
| 3 | 경로별 유효 관측을 보존하고 검증된 시간은 후속 경로 실패와 분리해 저장 | Q4에서 시각 확보→폼 실패→IR 실패여도 같은 행사의 정확한 시각 보존. 다른 행사·오래된 증거는 거절 |
| 4 | 인증 장벽을 실제 보이는 차단 상태로 판정하고 경로별 보호 대기를 분리 | 숨은captcha iframe은 정상 페이지 전체를 차단하지 않음. 실제 인증 장벽은 우회하지 않고 다른 유효 경로를 평가 |
| 5 | 이미 검증한 직접 제공사 후보를 행사별로 관리하고 실패한 단계부터 복구 | IR막힘이 같은 행사 직접폼 재시도를 무조건 막지 않음. 신선도·종목·날짜·행사ID 확인은 유지 |
| 6 | live/대기/종료/replay/unknown과 실패 단계를 별도로 보존 | 동일 행사 재방송을 live로 세지 않음. 마지막 경로 오류가 앞선 폼·시각 문제의 증거를 덮지 않음 |

CTAS 슬래시 비교, GIS 회사 메뉴 포털, PAYX 승격API·종료 규칙처럼 이미 수정된 부분은 그 상태를 유지하고 관련 회귀 사례로 남긴다. 이번에 새로 확인한 위 결함은 원인과 재현까지 확인했으며 운영 수정은 하지 않았다.

## 이번 분석의 검증 범위

- 과거 attempt·단계별 로그·DB 변경 이력·저장된 텍스트를 대조했다.
- 원본 등록 함수를 실제 Chromium으로 호출해 정상 텍스트 입력의 드롭다운 오판을 재현했다.
- 정상 화면+숨은 인증 iframe으로 CAPTCHA 오탐을 재현했다. 당시 실제 차단 여부는 미확정으로 유지했다.
- 당시 COST 관측과 원본 경로 순회 함수로 시각 전달 소실을 재현했다.
- 실제 GIS 관측과 현행 검증 함수로 주소→datetime 변환을 재현했고 DB이력도 일치했다.
- 외부 폼 제출·새 방송 재생·원본 코드 수정·운영 DB 갱신·서버 재시작은 하지 않았다.

세부 타임라인과 증거는 `.runtime/failure-audit-20260927/`의 종목별 보고서와 재현 로그에 보존한다.
